# ACI Dashboard - Design (draft)

Status: design only, no code yet. Branch: `feature/ACI`.

## 1. Goal

A read-only, searchable, static-HTML view of the Cisco ACI configuration (and later endpoints) for each ACI site, like a read-only APIC GUI. Main pages:

- **ACI sites** - list of sites with ACI. Each has a topology subpage: spine > leaf > compute.
- **Clusters** - one page per compute cluster (Nutanix `ntnx#`, Nutanix AI `nai#`) with switches, ports, policy groups, AAEPs, VLANs, EPGs. Every level expands to child objects.
- **Explorer + search** - any APIC object, its attributes and related objects (up and down), searchable like Search Clients.

Core rule: the collector and parsers never decide what the UI can show. Raw data is stored untouched; views are added later without re-collecting.

## 2. Constraints

- Python 3.12, `requests` allowed, otherwise standard library. No `netmiko` for ACI. If `requests` is not already installed on the offline server, use the standard library (`urllib`) so nothing has to be installed.
- **Offline, hand-carried, minimal code:** everything is copied by hand to an offline system. Few files, small readable modules, reuse existing functions, no network installs, no CDN or web fonts, no git needed on the target, a version string in each file, safe defaults for every new setting. Anything carried back out for review (probe results) must be small and sanitized.
- **Stay inline with the current architecture:** ACI is another orchestrator action (like `configs`), all writes go through the write queue into `sad.db`, and pages are generated by the same "Generate dashboard" action.
- Front end: vanilla HTML/CSS/JS only, no web server. Pages are opened from a network share (file://), so data loads through `<script>` tags (same approach as `config_viewer.py`).
- Windows Server, 2 admins on one install (remote sessions), manual runs. 2 sites (one APIC cluster each), under ~30 leafs each, ACI 6.x.
- APIC login: the existing credential store (`tacacs` entry, optional `aci` override, optional login domain). Read-only account only; this feature never writes to the APIC. APIC certs are self-signed: use a pinned PEM file as `verify=`; a `verify_tls` setting is the explicit escape hatch.

## 3. Architecture

1. **Collector** (`aci_collect.py`) - pulls APIC data and sends each result to the write queue as a raw row (compressed, hashed, not stored if identical to the newest). Takes plain arguments (credentials, progress function); it does not import `orchestrator`, so there is no circular import.
2. **Graph builder** (`aci_graph.py`) - builds generic entities (keyed by full DN) and edges in memory from the latest raw pull: containment from the DN, plus an edge for every relation object (`...Rs...` with a `tDn`). Nothing derived is stored. No class-specific code. DN splitting must ignore `/` inside `[...]` (e.g. `pathep-[eth1/5]`). Overrides and anchors are applied as an overlay.
3. **Views** - traversals over the graph (start, edge types, depth). New views need no new collection.
4. **Generator** (`aci_pages.py` + one HTML template) - writes static pages plus data files: a small search/navigation index loaded up front, entity details and adjacency in `.js` files loaded on demand. The UI lives in the template; Python only emits data. Site topology reuses `topology_svg.render_svg(layout, devices)` by building its plain-dict inputs.

## 4. Collection plan

- **Config: one whole query**, `GET /api/mo/uni.json?rsp-subtree=full&rsp-prop-include=config-only`. It returns the entire policy configuration (access policies, physical/L2/L3/VMM domains, tenants, fabric policies) with no list of roots to maintain. No fallback is built in; if the APIC refuses or times out, the plan is adjusted then (likely by splitting per top-level child of `uni`).
- **Operational allowlist** (in settings; not under `uni`): `fabricNode`, `fabricExplicitGEp` (vPC pairs), path objects, `lldpAdjEp`, `cdpAdjEp`.
- **Endpoints** (phase 3): paged `fvCEp` with children (`fvIp`, `fvRsCEpToPathEp`). Parsed into their own table, raw optional.
- **Site to APIC mapping** is in settings, keyed by site octet. Sites with no APIC entry are skipped with a "skipped" status.
- Query options (general APIC knowledge, confirm in probe): `rsp-subtree`, `rsp-prop-include=config-only` (avoids hash churn from operational fields; if modified-time style properties still change the hash, strip them before hashing), `page`/`page-size` for class queries. A single-object subtree query cannot be paged.

## 5. Clusters and anchors

ACI has no "compute cluster" object. A cluster = one or more **anchor objects with a role**: today each cluster has its own data AAEP and its own IPMI AAEP (and its own EPG in one AP). Port role (data/IPMI) comes from which anchor AAEP the port's policy group points to, not from names. Naming rules (`ntnx1...node1`, `...nodea`, `nai1...`) are an optional helper that suggests anchors; an admin confirms them. Standalone servers/firewalls that match nothing appear under "Unclassified" and can be assigned by hand. Data ports use vPC policy groups; IPMI uses access policy groups.

## 6. Port and endpoint views

- **Port view:** LLDP/CDP hostname (DNS can add FQDN), role, interface policies (from the policy group's relations), AAEP, VLAN and mode (`regular` = trunk, `native` = trunk native, `untagged` = access untagged) from static path bindings and AAEP-level bindings. A vPC path name equals its policy group name, so that one join is name-based (configurable join rule).
- **Endpoint view:** `fvCEp` carries `bdDn`, `fabricPathDn`, and tenant/AP/EPG in its DN; `fvIp` carries the IP, VRF and `createTs`. Add BD, VRF, contracts (EPG/ESG), AAEP(s), switch, interface by graph. VM names do not exist in ACI for non-VMM hosts; they come later from Prism, attached by MAC.

## 7. Sources, ranking, manual overrides

Every fact carries `source` and rank: `manual` > `policy` > `observed` (LLDP/CDP) > `dns` > future `prism`. Observed data does not overwrite configured data; disagreements show as "drift".

Admins can override any value shown on a page, add or hide an entity or edge, and define anchors, from **their own GUI tab** (`aci_tab.py`). Overrides are keyed by DN (or leaf+port) and survive re-pulls. Each is tagged `manual` with who/when, visible in the utility; the HTML shows a subtle marker. Edits go through the write queue and are logged with `db.log_activity`, like Site Manager's manual adds.

## 8. Storage

Decision: ACI tables live in `sad.db`, and every write goes through the existing write queue (strict parity with the rest of SAD). There is no separate `aci.db`.

- New actions are defined in a new module (`aci_db.py`) that creates its tables (`CREATE TABLE IF NOT EXISTS`) and registers its actions into `write_queue.ACTIONS` when imported. `db.py` and the queue code need no changes. An item for an action a process does not know waits in the queue until a process that imported `aci_db` drains it.
- A raw pull is one queue item per site: compressed JSON sent as text, with its hash, the same way config snapshots send config text. If the probe shows a compressed pull far larger than a few MB, split it into bounded chunks reassembled by the drain.
- Retention: keep everything. Identical pulls are not stored, so growth follows real config change. A `raw_keep_days` setting (empty = forever) plus a purge run only on request (GUI or CLI), never touching a site's first pull.
- Risks: `sad.db` grows with raw pulls (backups cover it; purge available). The drain lock is considered stale 120 s after it was claimed, so a long drain can be stolen. One optional small edit to `write_queue.py` (refresh the lock timestamp between items) removes this and also helps existing SAD.

## 9. Tables (sketch, in `sad.db`)

`aci_raw` (site_id, query, fetched_at, content_hash, payload_z, size_bytes), `aci_anchors` (site_id, cluster, role, dn, source, created_by, created_at), `aci_overrides` (site_id, dn, kind, value_json, action, created_by, created_at), and in phase 3 `aci_endpoints` and `aci_endpoint_moves`. Last-pull time comes from the newest `aci_raw` row; errors go to the activity log. Generic design means a new view needs no schema change.

## 10. Integration (files and edits)

New files: `utilities/aci_collect.py`, `utilities/aci_db.py`, `utilities/aci_graph.py`, `aci_pages.py`, `aci_template.html`, `aci_tab.py`.

Small edits to existing files, each given later as exact find/replace snippets:
- `orchestrator.py`: import, an `if "aci" in actions:` block in `_run_site_actions`, and `"aci"` in the CLI `--action` choices and the interactive menu.
- `gui.py`: one radio button on the Discovery tab, one entry in the progress-chip color table, a call to the ACI generator beside the `generate_config_pages` calls, and registering the new tab.
- `dashboard_generate.py`: an "ACI" link on the index page.
- Settings: an `aci` block (APIC address per site octet, login domain, `verify_tls`, PEM path, operational allowlist, `raw_keep_days`), in `settings.json` or a separate `aci_settings.json`.
- Optional: the lock-refresh edit to `write_queue.py` (section 8).

Rollback: delete the new files and revert those few lines. The tables are unused extras in `sad.db`.

## 11. Phases

0. **Probe:** the collector's first run with a report flag, run on the offline server against one APIC. It runs the whole-`uni` query and the operational allowlist, keeps the raw data on that server, and writes one compact "shape report" to carry out by hand: response size and timing, object counts per class, top-level children of `uni`, attribute names per class, and a few sample objects per key class with hostnames, IPs and MACs masked.
1. Collector action, raw store, graph, explorer, search, override data model.
2. Anchors, cluster pages, port/hardware view, site topology, overrides tab.
3. Endpoints, tracking (first/last seen, moves between pulls), endpoint view, DNS.
4. Change diffs between pulls.

## 12. To verify in the probe

- How a 6.x endpoint's effective ESG membership is exposed, and `pcTagAllocSrc` on `fvAEPg`.
- Whether VLANs sit on static path bindings, AAEP-level bindings, or both.
- What LLDP shows on Nutanix data and IPMI ports (BMC ports may show nothing).
- Compressed size and timing of the whole-`uni` pull, and whether hashes stay stable between identical pulls.

## 13. Staleness and tracking

Manual runs mean first/last seen reflect pulls, not real time; APIC timestamps such as `createTs` still give creation time. As elsewhere in SAD, stale is judged against the site's last successful pull, not today's date. Every page shows when each query was last pulled.

## 14. Open items

Whether `requests` is installed on the offline server (otherwise `urllib`), DNS scope (endpoint IPs only or LLDP/CDP names too), where endpoint search lives (own page or merged with Search Clients), ESG/contract detail depth, and Prism integration (kept possible by using generic "compute cluster/node" entities with a `platform` attribute and external IDs).
